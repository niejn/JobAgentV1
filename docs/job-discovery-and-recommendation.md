# JobAgent 岗位发现、每周推荐与投递资格设计

Boss 来源的具体 Adapter、CDP 方案和 Tool/MCP 决策见
[`boss-integration-design.md`](boss-integration-design.md)。

## 1. 目标

JobAgent 在取得 Resume/Candidate Background 与 Job Search Profile 后，可以长期执行岗位发现：
从 Boss、公司官网/ATS 等来源取得最新 Job Posting，去重后计算匹配度，每周向用户推荐值得进入
Opportunity Journey 的岗位。小红书在这一流程中主要提供面经与员工/内推线索，不作为权威 JD
来源；搜索结果必须回到 Boss 或公司官网核对具体岗位。

第一阶段仍由用户在 `jobagent chat` 中触发。真正的后台定时运行、通知和守护进程属于后续阶段，
不能仅靠 CLI 会话假装已经持续运行。

## 2. 启动资料门槛

启动时按缺失项引导，不一次询问已经保存的信息：

1. Resume 或已确认 Candidate Background：用于能力、经历和事实匹配。
2. Job Search Profile：至少包含期望岗位；可包含城市、薪资、公司特征、职位特征、行业、远程
   偏好、排除公司和其他硬约束。公司规模只是公司特征之一。
3. 可选目标 JD：用户已有具体岗位时直接创建一次 Opportunity Journey；没有 JD 时才进入岗位
   发现。

只有求职画像不能计算候选人匹配度；只有简历不能决定推荐范围。缺少任何一侧时可以帮助补齐，
但不能把不完整结果表述为可靠推荐。

### 2.1 特征不是单一标签

Company Feature 至少允许表达：

- 所有制/地域属性：外企、国内民企、国企、合资等。
- 行业与业务模式：互联网、AI、制造、金融科技、ToB/ToC、平台型/项目型。
- 发展阶段与规模层级：初创、成长、中型、大型；国内互联网还可使用大厂/中厂/小厂等用户
  能理解的分组，但必须保留分组依据。
- 经营和工程特征：盈利/融资阶段、技术驱动程度、研发投入、组织稳定性、工程文化。

Job Feature 至少允许表达：职能与职级、核心技术方向、业务线、平台/产品/交付性质、个人贡献者
或管理岗、创新/维护比例、成长空间、值班/出差/工作制度和岗位风险。特征既可以来自结构化字段，
也可以由模型从 JD 推断；推断结果必须带证据、置信度和“不确定”状态。

### 2.2 稳定偏好与动态策略分离

- Job Search Profile 保存用户明确给出或确认的长期偏好和硬约束。
- Search Strategy Portfolio 保存当前阶段如何分配热身、主目标和冲刺岗位，不修改原 Profile。
- 模型可以建议新特征或策略修订；建议必须展示推断依据，用户确认后才能升级为长期偏好。
- 阶段策略可以自动用于只读搜索和排序，但不能绕过硬约束，也不能授权自动投递。

## 3. 每周推荐运行

一次 Job Recommendation Run 是有界、可审计的长任务：

```text
读取最新 Candidate/Profile 版本
  -> 生成来源查询计划
  -> Boss / 公司官网采集最新 Job Posting
  -> 规范化公司、职位、地点与 JD
  -> Job Identity 去重及历史命中检查
  -> 硬约束过滤
  -> Candidate/JD 匹配与差距分析
  -> 排序并生成本周新增推荐
  -> 保存运行摘要、推荐与过滤原因
  -> 用户选择后创建 Opportunity Journey
```

长任务必须持久化运行状态、来源游标、预算和中间结果，支持失败后继续；每个来源继续使用独立
限流、退避和风控冷却。周报至少展示新增岗位、已见重复、适合/待确认/不适合、已投递过滤数，
不能每周重复推送相同岗位。

### 3.1 策略采用组合，而不是单一阶段开关

求职策略不应只有“现在是小公司阶段/大公司阶段”一个枚举，因为实际可能并行申请。每个策略
版本应表达三类组合及每周预算，例如：

| 组合 | 目的 | 示例（非固定规则） |
|---|---|---|
| Warm-up | 熟悉流程、验证表达与知识缺口 | 20%，岗位匹配较高、面试节奏合适 |
| Target | 当前最希望获得 offer 的主体岗位 | 60%，满足核心公司/职位特征 |
| Stretch | 更高平台、薪资或职责的冲刺岗位 | 20%，允许存在有限且可准备的差距 |

比例可以根据面试率、进入下一轮比例、失败原因、准备完成度、时间预算和用户反馈调整。所谓“小
公司练手”应建模为 Warm-up 目的，而不是把“小公司”永久等同于低价值；外企、国内大中小厂都
可能进入任一组合，取决于本次求职目标和岗位质量。

每次 Strategy Revision 保存：上一版本、调整前后组合、触发证据、模型建议理由、用户反馈、
生效时间和下次复查条件。没有足够反馈时保持当前策略，不为了“动态”而频繁漂移。

### 3.2 示例：小规模公司 Warm-up 的 Boss 直投路径

公司人数采用招聘平台常见区间作为原始特征，例如 `0–20`、`20–99`、`100–499`、`500–9999`、
`10000+`；这些区间不直接代表岗位价值。只有当前 Search Strategy Portfolio 明确把某批 0–20 或
20–99 人公司的岗位划入 Warm-up 组合时，才应用下列默认 Application Route：

```text
Boss 发现具体岗位与完整 JD
  -> 简历/JD 匹配与硬约束检查
  -> 生成该岗位 Tailored Resume（不修改基础简历）
  -> 生成针对性的 Boss 招呼语
  -> 用户查看岗位、简历版本、招呼语并 approve/edit/reject
  -> 获批后联系 HR、发送简历或执行平台投递
  -> 正向确认发送/投递成功后写入 Application
```

- 默认 `Referral Workstream = SKIPPED_BY_STRATEGY`，不花时间从小红书寻找内推人。
- `Interview Preparation Workstream` 独立决定；如果时间允许，仍可从小红书寻找该公司真实面经，
  不要把“无内推”错误理解为“禁止小红书研究”。
- Target/Stretch 或用户点名的公司可采用“内推优先，超时后 Boss/官网回退”的其他路径。
- 每个岗位保存最终采用的 Application Route 和原因，便于后续比较各渠道的回复率和面试率。

当前存量 Boss 投递实现仍需先完成 `plan.md` 的 CR-02：必须确认消息/简历实际发送成功，不能因
找到按钮或输入框就记录 `APPLIED`。在该可靠性问题关闭前，此流程只能生成草稿并等待人工操作，
不能声称已经自动投递。

Boss 只读发现使用 `/wapi/zpgeek/search/joblist.json` 的薄 Adapter，并保留 Playwright 抓取器作为
诊断/回退代码。Adapter 使用 Provider Cookie 自动匹配、公司规模官方代码、稳定 encryptJobId、
单请求串行限频和风控冷却；`code != 0` 时停止而不是切换指纹或重试。列表响应是候选岗位摘要，
完整匹配仍需后续取得具体 JD，不能把标签列表当作完整岗位描述。

## 4. 第一版去重

第一版 `Job Identity = normalized_company + normalized_role`：

- 同一公司、同一规范化职位在 Boss 和官网出现：一个 Job Identity，保留多个 Job Posting 来源。
- 同一公司、同一职位的 JD 更新或重新发布：仍是同一身份，新增 Posting 版本并重新计算匹配，
  仅在匹配结论或关键要求发生实质变化时再次提醒。
- 同一公司、不同职位：是两个 Job Identity，不应被去重掉。
- 公司简称、集团/子公司和职位别名先使用显式别名表；无法可靠归一时保留两个候选并标记待确认，
  不用 LLM 猜测后静默合并。

后续可把职级、城市、业务线、招聘平台岗位 ID 和 JD 语义指纹加入判定，但必须保留确定性解释与
人工拆分/合并能力。

## 5. 同公司多岗位不是去重问题

不同职位即使属于同一公司，也应分别保留并计算匹配度。是否允许投递由独立的 Application
Eligibility Policy 决定，投递 Agent 只消费判定结果并执行经 HITL 批准的动作。

第一版建议默认规则：

- 同公司已有 `APPLIED` 或 `INTERVIEWING` 岗位时，其他岗位仍可分析和推荐，但投递状态为
  `REQUIRES_REVIEW`，不得自动提交。
- 如果新岗位与已投岗位高度相似，提示可能被招聘系统视为重复申请，并列出差异。
- 如果新岗位属于明显不同职能或业务线，允许用户人工批准继续投递。
- 公司明确限制申请数量或冷却期时，以该公司的规则为准。
- 用户拒绝、撤回或岗位关闭不能与“从未投递”混为同一状态。

该策略后续应版本化，并在每次资格判断中记录命中的规则、历史 Application ID 与人工覆盖理由。

## 6. 分阶段实施

### R1：启动引导（当前）

- 空资料时主动询问简历、求职意向，也允许直接提供 JD。
- 已有 SQLite Candidate Profile 时只追问缺失项。
- Job Search Profile 支持用户确认的公司特征和职位特征；公司规模保留为兼容的细分字段。

### R2：手动触发岗位发现

- 建立 Job Posting、Job Identity 与 Recommendation Run 的 SQLite 表。
- 建立版本化 Search Strategy Portfolio；模型从 JD、投递和面试反馈提出带依据的 Strategy
  Revision，确定性规则保证硬约束优先。
- 将 Boss 与公司官网采集封装为只读 Job Discovery Tool。
- 实现确定性去重、硬约束过滤、匹配排序和 `/recommendations`。

### R3：每周长任务

- 增加持久化调度、断点续跑、来源游标和运行锁。
- 输出周报并记录用户反馈；通知默认只读，不执行自动投递。

### R4：投递资格与投递 Agent

- 建立 Application 与版本化 Application Eligibility Policy。
- 同公司多职位触发人工复核；提交简历仍必须 HITL。
- 结合实际招聘平台规则逐步增加冷却期、岗位相似度和公司级申请上限。
- 按 Search Strategy Portfolio 生成 Application Route；Warm-up 小规模公司默认可跳过 XHS 内推，
  经 HITL 后走 Boss 定制简历与直投；先修复 CR-02 的成功确认再开放自动执行。

## 7. Future work

- PostgreSQL 作为多进程业务状态库，Redis 用于分布式运行锁、限流和任务协调。
- S3/MinIO/OSS 保存 JD、分析报告、网页快照、XHS 原图与 OCR 输入；数据库保存元数据和 URI。
- 语义去重、向量检索或图数据库只能作为候选生成/索引，不能替代原始 Job Posting 与确定性历史。
